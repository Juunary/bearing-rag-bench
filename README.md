# bearing-rag-bench

한국어·영어·독일어가 섞인 베어링·자동차 부품 기술문서를 대상으로 RAG 검색 품질을 비교하는 실험 저장소입니다.
LangChain, LlamaIndex 같은 프레임워크 없이 청킹, BM25 토큰화, 임베딩, HNSW, RRF, 리랭킹, 지표 계산을 직접 구현했습니다.

## 재현

```bash
uv sync
uv run python scripts/fetch_data.py                 # 위키백과 45건 수집 (data/raw, 커밋 안 함)
uv run python -m ragbench.ingest                    # 정제 -> data/processed/docs.jsonl
uv run python -m ragbench.chunking                  # 384토큰 청크 346개
uv run python scripts/validate_eval.py              # 평가셋 검사
```

실험 1개는 설정 파일 1개와 명령 1줄입니다.

```bash
uv run python experiments/run_retrieval.py configs/s1_hybrid_rrf_rerank.json
```

전체 실행과 표 생성입니다.

```bash
for c in configs/s1_*.json; do uv run python experiments/run_retrieval.py $c; done
uv run python experiments/run_hnsw_sweep.py
uv run python experiments/compare.py experiments/results/s1_*.json --by-group
uv run python experiments/analyze_s1.py             # 이 문서의 신뢰구간·실패 목록
uv run pytest -q
```

결과 JSON에는 설정 전체, 패키지 버전, git 커밋(미커밋 변경이 있으면 `-dirty`), 모델 리비전, 시드, 질문별 순위가 들어 있습니다.
시드는 42로 고정했습니다. GPU 커널 차이로 소수점 아래 수치가 달라질 수 있습니다.

## 데이터

- **출처**: 위키백과 한국어 13건, 영어 16건, 독일어 16건, 총 45건(CC BY-SA 4.0). 목록은 `data/sources.csv`, 수집한 리비전 ID는 `data/processed/docs.jsonl`에 있습니다.
- **청크**: 영어 179개, 독일어 124개, 한국어 43개, 총 346개. 한국어가 적은 이유는 한국어 위키의 베어링 문서가 짧고 적기 때문입니다.
- **제외한 것**: 제조사 카탈로그 PDF는 1단계에서 뺐습니다. Schaeffler 공식 PDF는 스크립트 다운로드가 403으로 막혔고, PDF 정제에 쓸 시간이 없었습니다. 따라서 이 저장소의 결과는 백과사전 문체 문서에 대한 것이며 제조사 기술 문서에는 확인되지 않았습니다.
- **한국어 문서의 성격**: `ko_ball_bearing`은 영어 Ball bearing 문서의 번역입니다. 같은 사실이 두 언어에 있는 경우가 있어 평가셋에서 동의 근거를 함께 정답으로 적었습니다.

## 실험 설계

### 청킹
- 길이는 bge-m3 토크나이저 기준 384토큰, 겹침은 48토큰입니다.
- 한국어는 영어·독일어보다 같은 내용에 토큰이 약 2.6배 듭니다(측정: 한국어 1.7자/토큰, 영어·독일어 4.1~4.4자/토큰). 문자 수 기준이면 한국어 청크의 내용이 적어지므로 토큰 기준을 택했습니다.
- 문단·문장 경계에서 자르고, 겹침도 문장 단위입니다. 문장이 한도를 넘을 때만 강제로 자릅니다.
- 문서·절 제목은 청크에 붙이지 않았습니다. 2단계 contextual retrieval 비교의 기준선으로 남겼습니다.

### 검색 4종
| 방식 | 구현 |
|---|---|
| BM25 | bm25s 0.3.13, k1=1.5, b=0.75. 토크나이저 3종(공백, kiwipiepy 0.24.0 형태소, bge-m3 서브워드)을 주입식으로 비교 |
| dense | BAAI/bge-m3. CLS 풀링 후 L2 정규화, 내적 = 코사인. hnswlib 0.8.0(m=16, ef_construction=128, ef_search=64)과 전수검색을 둘 다 실행 |
| 하이브리드 | BM25(형태소)와 dense를 RRF로 융합. 점수 = Σ 1/(k+순위), k=60, 후보 각 50개 |
| 하이브리드 + 리랭커 | 위 융합의 상위 30개를 BAAI/bge-reranker-v2-m3 cross-encoder로 재정렬 |

### 평가셋 (`eval/queries.jsonl`)
- 질문 45개: 한·영·독 각 15개. 주 근거 기준 단일 언어 21개, 교차 언어 24개입니다.
- 정답은 청크 ID가 아니라 "문서 ID + 근거 문장 원문 + 등급"으로 적었습니다. 평가할 때 그 문장을 50% 이상 덮는 청크를 정답으로 자동 매핑하므로, 청킹을 바꿔도 평가셋은 그대로 씁니다.
- 등급은 핵심 근거 2, 보조 근거 1입니다. 정답 목록의 첫 항목이 주 근거이고, 그 문서의 언어가 단일/교차와 집계 그룹을 정합니다.


### 지표 (`src/ragbench/metrics.py`, 직접 구현)
- **Recall@5**: 상위 5개에 든 정답 청크 수 / 전체 정답 청크 수.
- **MRR@10**: 첫 정답 순위의 역수. 등급은 보지 않습니다.
- **nDCG@10**: 선형 gain(등급/log2(순위+1)). 이상적 순서의 DCG도 k에서 잘라 계산합니다.
- 손계산 기대값을 `tests/test_metrics.py`에 두었습니다.

### 한국어 BM25 토큰화
- 한국어 단일 언어 질문은 3개뿐이라 토크나이저 간 우열을 말할 수 없습니다(nDCG 공백 0.78, 형태소 0.83, 서브워드 0.83).
- 전체 단일 언어 21문항에서도 세 토크나이저는 0.78~0.80으로 사실상 같습니다. "형태소 분석이 조사 문제를 풀어 한국어 BM25를 크게 개선한다"는 가설은 이 데이터로 입증되지 않았습니다.
- 비용 차이는 뚜렷합니다. 인덱스 빌드 시간은 공백 0.04초, 형태소 1.78초, 서브워드 10.65초입니다.

### HNSW 파라미터 (346벡터, 평가셋 질문 45개, 전수검색 대비 recall@10)

| ef_search | recall@10 평균 | 질의당 p50 지연 평균 |
|---|---|---|
| 16 | 0.951 | 0.020 ms |
| 64 | 1.000 | 0.039 ms |
| 128 | 1.000 | 0.056 ms |
| 256 | 1.000 | 0.075 ms |

- ef_search=64 이상에서는 m(8, 16, 32)과 ef_construction(64, 128, 256) 조합 27개(전체 36개 중 ef_search 16을 뺀 것) 모두 recall이 1.000입니다. recall이 1 미만인 것은 ef_search=16인 9개 조합뿐이고 0.938~0.957 범위입니다.
- 인덱스 크기는 m=8 1413KB, m=16 1434KB, m=32 1477KB입니다. 벡터 원본은 1384KB입니다.
- 전수검색은 질의당 p50 0.040 ms이고, HNSW는 0.018~0.087 ms입니다. ef_search=16은 전수검색보다 빠르고 64는 같은 수준, 128 이상은 더 느립니다. 이 규모에서는 HNSW의 속도 이점이 거의 없습니다.
- dense 실험에서 HNSW와 전수검색의 상위 10개 목록은 45개 질문 모두 같았습니다.
- **재현성 주의**: hnswlib를 기본 설정(전체 코어)으로 만들면 실행할 때마다 그래프가 달라집니다. 테스트에서 질문 60개 중 31개가 5번 빌드에서 상위 50개 목록이 달랐고, 이 변동이 하이브리드 결과에도 전해졌습니다(Recall@5 0.411 → 0.422). 단일 스레드(`num_threads=1`)로 고정한 뒤에는 전체 실험을 두 번 돌려 모든 순위가 같았습니다.
- 벡터가 346개라 recall이 포화된 것이며, 파라미터가 무의미하다는 뜻이 아닙니다. 규모 효과는 측정하지 못했습니다.

## 실패 사례와 원인 분석

**1. BM25는 교차 언어에서 작동하지 않습니다.**
교차 언어 24문항에서 nDCG가 0.09~0.10입니다. 질문과 문서가 다른 언어면 공유하는 어휘가 거의 없기 때문입니다. de→en의 0.48은 예외인데, 해당 질문에 Brinelling, DIN 3761, needle 같은 공통 고유명사가 들어 있어 어휘가 겹친 결과입니다. 즉 이 0.48은 교차 언어 능력이 아니라 평가셋 구성의 결과입니다.

**2. RRF는 교차 언어에서 dense보다 나빴습니다.**
- 사실: 정답이 dense 상위 5에 있었는데 RRF 상위 5에서 빠진 질문이 11개이고, 11개 모두 교차 언어입니다. 반대로 RRF가 나은 질문은 4개입니다. 교차 언어 nDCG는 dense 0.345, RRF 0.092입니다.
- 원인(순위 단위로 확인): 정답 청크는 dense 목록에만 있고, 질문과 같은 언어의 청크는 BM25와 dense 양쪽에 올라 점수가 합쳐집니다. k=60에서는 1등(1/61)과 5등(1/65)의 점수 차이가 작아, 두 목록에 중간 순위로 같이 오른 청크가 한 목록의 1등을 이깁니다.
- 임시 확인: k를 60, 10, 1로 바꿔 보면 교차 언어 nDCG가 0.092, 0.174, 0.250으로 올랐고 단일 언어는 0.808, 0.820, 0.835로 소폭 올랐습니다. 이 계산은 결과 파일로 남기지 않은 임시 실행이고 질문 45개로 k를 고르면 평가셋에 맞춘 값이 되므로, 정식 실험으로 넣지 않았습니다.

**3. 리랭커가 가장 좋지만 같은 언어 쪽으로 기웁니다.**
RRF+리랭커가 상위 5에 정답을 하나도 넣지 못한 질문이 9개입니다. 9개 모두 1위 청크가 질문과 같은 언어입니다. 정답이 독일어에 있는 질문(ko→de 3개, en→de 3개)이 6개로 가장 많습니다.
- 확인된 것: 이 9개 질문에서 1위가 질문 언어의 문서였습니다.
- 가설(미검증): 영어·한국어 질문에는 같은 주제를 다루는 같은 언어 문서가 따로 있어, 독일어 문서에만 있는 세부 사실이 밀립니다. en→ko와 de→ko는 한국어 문서가 적고 짧아 dense 점수가 높게 나왔습니다(0.94, 0.74).
- 단, en→de의 dense 0.00은 질문 4개의 결과라 일반화하지 않습니다.

**4. 정제 실패가 일부 청크를 오염시킵니다.**
수식이 한 글자씩 쪼개져 들어온 청크가 대략 35개입니다(1~2자짜리 줄이 30줄을 넘는 청크로 센 근사치이며 정확한 오염 비율이 아닙니다). 예: `ko_bearing#5`는 Weibull 분포 수식의 조각으로 채워져 있습니다. 위키 TextExtracts가 수식과 표를 평문으로 바꾸는 과정에서 생겼고, 해당 청크는 임베딩과 BM25 품질을 떨어뜨립니다. 정제 개선 전후 비교는 하지 않았습니다.

**5. 평가셋 검수에서 나온 문제.**
표본 12개 중 2개가 부적합했습니다. 하나는 "이와 같은" 같은 지시어 때문에 앞 문맥 없이는 의미가 불완전한 문장을 핵심 근거로 쓴 것, 다른 하나는 '왜'를 묻는데 원인이 아닌 발생 조건 문장을 핵심 근거로 쓴 것입니다. 같은 유형이 나머지 33개에도 남아 있을 수 있습니다.

## 한계

- **표본 크기**: 질문 45개, 언어쌍별로는 2~9개입니다.
- **정답 누락**: 같은 사실이 다른 언어 문서에 더 있는데 정답으로 적지 못한 경우는 부당하게 오답 처리됩니다.
- **규모**: 346벡터에서 HNSW 효과를 볼 수 없었습니다.
- **측정 범위**: 검색 단계만 평가했습니다. 답변 생성, 사실성, 운영 지표는 측정하지 않았습니다.
