# bearing-rag-bench

한국어·영어·독일어가 섞인 베어링·자동차 부품 기술문서를 대상으로 RAG 검색 품질을 비교하는 실험 저장소입니다.
LangChain, LlamaIndex 같은 프레임워크 없이 청킹, BM25 토큰화, 임베딩, HNSW, RRF, 리랭킹, 지표 계산을 직접 구현했습니다.

## 재현

```bash
uv sync
uv run python scripts/fetch_data.py                 # 위키백과 45건 수집 (data/raw, 커밋 안 함)
uv run python -m ragbench.ingest                    # 정제 -> data/processed/docs.jsonl
uv run python -m ragbench.chunking                  # 384토큰 청크 346개
uv run python scripts/validate_eval.py              # 평가셋 검사
```

실험 1개는 설정 파일 1개와 명령 1줄입니다.

```bash
uv run python experiments/run_retrieval.py configs/s1_hybrid_rrf_rerank.json
```

전체 실행과 표 생성입니다.

```bash
for c in configs/s1_*.json; do uv run python experiments/run_retrieval.py $c; done
uv run python experiments/run_hnsw_sweep.py
uv run python experiments/compare.py experiments/results/s1_*.json --by-group
uv run python experiments/analyze_s1.py             # 이 문서의 신뢰구간·실패 목록
uv run pytest -q
```

생성과 운영(3, 3.5단계)입니다. 생성기는 GPU 한 장(7.5GiB)이 필요합니다.

```bash
uv run python experiments/run_generation.py configs/s3_gen_cite_refuse_v1.json   # 답변 생성
uv run python experiments/run_pipeline.py configs/s35_pipeline.json              # 캐시·검증·로깅 포함 전체 경로
uv run python experiments/regression.py configs/s3_gen_cite_refuse_v1.json --run # 다시 돌리고 기준선과 비교
```

평가와 파인튜닝(3, 4단계)입니다. 판정 모델은 GPU 2장에 나눠 올리고, 데이터 생성은 GPU 2장을 씁니다.

```bash
uv run python experiments/run_judge.py configs/s3_judge.json s3_gen_cite_v1 s3_gen_cite_refuse_v1   # LLM 판정과 결과 유형 분류
uv run python experiments/analyze_judge.py                                        # 사람 채점(eval/human_labels.json)과 일치도
uv run python experiments/build_sft_data.py                                       # 학습 데이터 생성 (약 45분, 커밋된 data/sft로 건너뛸 수 있음)
uv run python experiments/train_lora.py configs/s4_qlora_r16.json                 # QLoRA 학습 (약 10분, 최대 4.3GiB)
uv run python experiments/train_lora.py configs/s4_lora_r16.json                  # LoRA 학습 (약 10분, 최대 9.4GiB)
for c in s4_gen_base4bit s4_gen_qlora_r16 s4_gen_lora_r16; do uv run python experiments/run_generation.py configs/$c.json; done
uv run python experiments/run_judge.py configs/s3_judge.json s4_gen_base4bit s4_gen_qlora_r16 s4_gen_lora_r16
uv run python experiments/analyze_s4.py
```

결과 JSON에는 설정 전체, 패키지 버전, git 커밋(미커밋 변경이 있으면 `-dirty`), 모델 리비전, 시드, 질문별 순위가 들어 있습니다.
시드는 42로 고정했습니다. GPU 커널 차이로 소수점 아래 수치가 달라질 수 있습니다.

## 데이터

- **출처**: 위키백과 한국어 13건, 영어 16건, 독일어 16건, 총 45건(CC BY-SA 4.0). 목록은 `data/sources.csv`, 수집한 리비전 ID는 `data/processed/docs.jsonl`에 있습니다.
- **청크**: 영어 179개, 독일어 124개, 한국어 43개, 총 346개. 한국어가 적은 이유는 한국어 위키의 베어링 문서가 짧고 적기 때문입니다.
- **제외한 것**: 제조사 카탈로그 PDF는 1단계에서 뺐습니다. Schaeffler 공식 PDF는 스크립트 다운로드가 403으로 막혔고, PDF 정제에 쓸 시간이 없었습니다. 따라서 이 저장소의 결과는 백과사전 문체 문서에 대한 것이며 제조사 기술 문서에는 확인되지 않았습니다.
- **한국어 문서의 성격**: `ko_ball_bearing`은 영어 Ball bearing 문서의 번역입니다. 같은 사실이 두 언어에 있는 경우가 있어 평가셋에서 동의 근거를 함께 정답으로 적었습니다.

## 실험 설계

### 청킹
- 길이는 bge-m3 토크나이저 기준 384토큰, 겹침은 48토큰입니다.
- 한국어는 영어·독일어보다 같은 내용에 토큰이 약 2.6배 듭니다(측정: 한국어 1.7자/토큰, 영어·독일어 4.1~4.4자/토큰). 문자 수 기준이면 한국어 청크의 내용이 적어지므로 토큰 기준을 택했습니다.
- 문단·문장 경계에서 자르고, 겹침도 문장 단위입니다. 문장이 한도를 넘을 때만 강제로 자릅니다.
- 문서·절 제목은 청크에 붙이지 않았습니다. 2단계 contextual retrieval 비교의 기준선으로 남겼습니다.

### 검색 4종
| 방식 | 구현 |
|---|---|
| BM25 | bm25s 0.3.13, k1=1.5, b=0.75. 토크나이저 3종(공백, kiwipiepy 0.24.0 형태소, bge-m3 서브워드)을 주입식으로 비교 |
| dense | BAAI/bge-m3. CLS 풀링 후 L2 정규화, 내적 = 코사인. hnswlib 0.8.0(m=16, ef_construction=128, ef_search=64)과 전수검색을 둘 다 실행 |
| 하이브리드 | BM25(형태소)와 dense를 RRF로 융합. 점수 = Σ 1/(k+순위), k=60, 후보 각 50개 |
| 하이브리드 + 리랭커 | 위 융합의 상위 30개를 BAAI/bge-reranker-v2-m3 cross-encoder로 재정렬 |

### 평가셋 (`eval/queries.jsonl`)
- 질문 45개: 한·영·독 각 15개. 주 근거 기준 단일 언어 21개, 교차 언어 24개입니다.
- 정답은 청크 ID가 아니라 "문서 ID + 근거 문장 원문 + 등급"으로 적었습니다. 평가할 때 그 문장을 50% 이상 덮는 청크를 정답으로 자동 매핑하므로, 청킹을 바꿔도 평가셋은 그대로 씁니다.
- 등급은 핵심 근거 2, 보조 근거 1입니다. 정답 목록의 첫 항목이 주 근거이고, 그 문서의 언어가 단일/교차와 집계 그룹을 정합니다.


### 지표 (`src/ragbench/metrics.py`, 직접 구현)
- **Recall@5**: 상위 5개에 든 정답 청크 수 / 전체 정답 청크 수.
- **MRR@10**: 첫 정답 순위의 역수. 등급은 보지 않습니다.
- **nDCG@10**: 선형 gain(등급/log2(순위+1)). 이상적 순서의 DCG도 k에서 잘라 계산합니다.
- 손계산 기대값을 `tests/test_metrics.py`에 두었습니다.

### 한국어 BM25 토큰화
- 한국어 단일 언어 질문은 3개뿐이라 토크나이저 간 우열을 말할 수 없습니다(nDCG 공백 0.78, 형태소 0.83, 서브워드 0.83).
- 전체 단일 언어 21문항에서도 세 토크나이저는 0.78~0.80으로 사실상 같습니다. "형태소 분석이 조사 문제를 풀어 한국어 BM25를 크게 개선한다"는 가설은 이 데이터로 입증되지 않았습니다.
- 비용 차이는 뚜렷합니다. 인덱스 빌드 시간은 공백 0.04초, 형태소 1.78초, 서브워드 10.65초입니다.

### HNSW 파라미터 (346벡터, 평가셋 질문 45개, 전수검색 대비 recall@10)

| ef_search | recall@10 평균 | 질의당 p50 지연 평균 |
|---|---|---|
| 16 | 0.951 | 0.020 ms |
| 64 | 1.000 | 0.039 ms |
| 128 | 1.000 | 0.056 ms |
| 256 | 1.000 | 0.075 ms |

- ef_search=64 이상에서는 m(8, 16, 32)과 ef_construction(64, 128, 256) 조합 27개(전체 36개 중 ef_search 16을 뺀 것) 모두 recall이 1.000입니다. recall이 1 미만인 것은 ef_search=16인 9개 조합뿐이고 0.938~0.957 범위입니다.
- 인덱스 크기는 m=8 1413KB, m=16 1434KB, m=32 1477KB입니다. 벡터 원본은 1384KB입니다.
- 전수검색은 질의당 p50 0.040 ms이고, HNSW는 0.018~0.087 ms입니다. ef_search=16은 전수검색보다 빠르고 64는 같은 수준, 128 이상은 더 느립니다. 이 규모에서는 HNSW의 속도 이점이 거의 없습니다.
- dense 실험에서 HNSW와 전수검색의 상위 10개 목록은 45개 질문 모두 같았습니다.
- **재현성 주의**: hnswlib를 기본 설정(전체 코어)으로 만들면 실행할 때마다 그래프가 달라집니다. 테스트에서 질문 60개 중 31개가 5번 빌드에서 상위 50개 목록이 달랐고, 이 변동이 하이브리드 결과에도 전해졌습니다(Recall@5 0.411 → 0.422). 단일 스레드(`num_threads=1`)로 고정한 뒤에는 전체 실험을 두 번 돌려 모든 순위가 같았습니다.
- 벡터가 346개라 recall이 포화된 것이며, 파라미터가 무의미하다는 뜻이 아닙니다. 규모 효과는 측정하지 못했습니다.

### 지연 (질문 1개, ms)

| 방식 | p50 | p95 |
|---|---|---|
| BM25 (3종) | 0.09~0.20 | 0.12~0.68 |
| dense | 7.9 | 9.1 |
| 하이브리드 RRF | 8.6 | 9.4 |
| RRF + 리랭커 | 168.4 | 182.1 |

dense의 지연은 대부분 질문 임베딩 계산입니다. 리랭커는 후보 30개를 매번 cross-encoder로 계산하므로 dense의 약 20배입니다.

## 생성, 평가, 운영 (3단계, 3.5단계)

### 답변 생성
- 모델: Qwen3-4B-Instruct-2507(Apache 2.0, 4.02B 파라미터, bf16 7.5GiB), 로컬 실행, greedy 디코딩.
- 컨텍스트: RRF+리랭커 검색의 상위 5개 청크. 프롬프트는 평균 약 2000토큰입니다.
- 프롬프트 2종: 근거 인용 강제(cite_v1), 인용 강제 + 근거 없으면 정확히 NO_ANSWER만 출력(cite_refuse_v1).

| 자동 지표 (45문항) | cite_v1 | cite_refuse_v1 |
|---|---|---|
| 답변에 인용이 있음 | 97.8% | 91.1% |
| 정답 청크를 인용함 | 75.6% | 75.6% |
| 정답 청크가 프롬프트에 있음 (검색 상한) | 80.0% | 80.0% |
| 거절 (NO_ANSWER) | 0% | 8.9% |
| 생성 시간 중앙값 | 3.6초 | 2.9초 |

- 정답 청크가 프롬프트에 있던 36개 질문에서는 94%가 정답 청크를 인용했고, 없던 9개에서는 0%였습니다. 이 9개는 프롬프트가 아니라 검색을 고쳐야 합니다.
- 위 지표는 형식과 근거 연결만 봅니다. 답의 정확성, 충실도, 관련성은 아래 평가에서 따로 판정했습니다.
- 같은 입력을 두 번 돌리면 답변 45개가 모두 같았습니다(greedy, 배치 1).

### 답변 평가 (LLM 판정과 사람 채점)

- 판정 모델: Qwen3-8B(Apache 2.0, 8.2B), GPU 2장에 나눠 로드, 생각 모드 끔, greedy. 생성 모델(4B)과 다른 더 큰 모델을 써서 자기 답변을 후하게 채점하는 편향을 줄였지만 같은 모델 계열입니다.
- 판정 항목 4개를 항목마다 별도 프롬프트로 예/아니오 판정합니다: 충실도(주장이 인용 청크로 뒷받침되는가), 답변 관련성, 컨텍스트 관련성(5개 청크에 답에 필요한 정보가 있는가), 정확성(평가셋의 정답 문장과 일치하는가). 거절 답변은 앞의 세 항목에서 제외합니다.
- 사람 채점: 사용자가 답변 8개를 정확성, 충실도, 답변 관련성으로 채점했습니다(`eval/human_labels.json`). 채점표에는 판정 모델의 결과를 넣지 않았습니다.

| 판정 결과 (답변 45개) | 충실도 | 답변 관련성 | 컨텍스트 관련성 | 정확성 |
|---|---|---|---|---|
| cite_v1 | 92.5% (n=40) | 97.5% (n=40) | 88.9% (n=45) | 85.0% (n=40) |
| cite_refuse_v1 | 95.0% (n=40) | 100% (n=40) | 88.9% (n=45) | 80.0% (n=40) |

n은 해당 항목이 적용되는 답변 수입니다. 판정 모델의 컨텍스트 관련성은 정답 청크 유무와 45개 중 39개(86.7%)가 일치했습니다.

**사람과 판정 모델의 일치** (8개 중 판정 모델이 평가하는 답변)

| 항목 | 일치 | 비교 가능 |
|---|---|---|
| 정확성 | 7 | 7 |
| 답변 관련성 | 7 | 7 |
| 충실도 | 5 | 7 |

- 충실도 불일치 2건은 모두 판정 모델이 더 후하게 본 경우이고, 둘 다 정답 청크가 프롬프트에 없던 질문입니다. 하나는 답은 맞았지만 인용 청크에는 근거가 없었습니다. 모델이 자기 지식으로 답한 사례입니다.
- 표본 밖에서도 판정 오류가 보였습니다. 청크 문장을 그대로 옮긴 답을 틀렸다고 판정한 경우(q037)와, 판정 이유가 기준 문장에 없는 단어를 인용한 경우(q044)입니다. 숫자는 고치지 않았으므로 위 비율은 근사치이고 특히 충실도는 과대평가됐을 가능성이 큽니다.
- 8개 표본과 채점자 1명이라 일치도는 개수로만 보고합니다.

**결과 유형** (두 프롬프트가 같은 개수)

| 유형 | 개수 | 고칠 곳 |
|---|---|---|
| ok | 29 | |
| 생성 실패 (정답 청크가 있는데 틀리거나 근거 없음) | 6 | 프롬프트·모델 |
| 검색 실패 (정답 청크 없이 답함) | 5 | 검색 |

- 두 프롬프트의 유형 개수가 같지만 답변은 45개 중 9개만 같습니다. 프롬프트가 영향이 없다는 뜻이 아니라, 이 표본으로는 차이를 가려낼 수 없다는 뜻입니다.
- 검색 실패 5건 중 3건은 정답으로 판정됐습니다. 정답 목록이 같은 사실을 담은 다른 청크를 다 담지 못한 것이므로 검색 실패 수는 상한입니다.
- 생성 실패 6건은 공통 원인이 없습니다. 문장 뜻을 거꾸로 읽음, 다른 문서의 내용을 섞음, 조인트 종류를 틀림, 한국어 용어를 독일어로 옮기며 깨뜨림 등입니다. 6건 모두 정답 청크를 인용했으므로 인용 형식 문제는 아닙니다.

### 운영 기능

질문 한 건의 경로는 입력 검사, 검색, 프롬프트 구성, 캐시 조회(미스면 생성), 출력 검사, 로그 기록입니다(`src/ragbench/pipeline.py`).

| 기능 | 구현 | 측정 결과 |
|---|---|---|
| 요청 로깅 | 질문, 검색 청크와 점수, 프롬프트, 원본·최종 답변, 차단 사유, 캐시 여부, 단계별 지연, 토큰 수, 모델·리비전을 JSONL 한 줄로 기록(`logs/`, git 제외) | 90건(2회차) 기록 확인 |
| LLM 캐시 | SQLite. 키는 모델 리비전, 프롬프트 전문, 길이 제한, 디코딩 방식의 해시 | 2회차 45건 모두 히트, 답변 동일. 질문당 지연 중앙값 3212ms에서 176ms |
| 입출력 검증 | 빈 입력·1000자 초과 차단. 답변은 빈 답, 센티널·자연어 거절, 프롬프트에 없던 청크 인용, 인용 없음이면 고정 문구로 교체 | 45건 중 5건 차단(센티널 4, 자연어 거절 1) |

차단 5건을 정답 청크의 유무로 나누면 다음과 같습니다.

| | 차단됨 | 통과 |
|---|---|---|
| 정답 청크가 프롬프트에 있음 (36) | 1 (과잉 거절) | 35 |
| 정답 청크가 프롬프트에 없음 (9) | 4 | 5 |

- 근거 없이 답한 5건은 형식이 올바른 인용을 달고 검증을 통과했습니다. 이런 답은 규칙으로 막을 수 없고 충실도 채점이 필요합니다.
- 회귀 기준을 정확한 일치로 둔 근거는 이 저장소의 검색과 생성이 결정적이라는 점입니다. 파이프라인의 원본 답변과 컨텍스트는 3단계 결과와 45건 모두 같았습니다.
- 코퍼스에 답이 없는 질문을 평가셋에 넣지 않아서, 거절이 옳았는지는 정답 청크 유무로 대신 추정했습니다.

## LoRA / QLoRA 파인튜닝 (4단계)

**과제**: 근거 인용 완결성입니다. 답변의 모든 문장 끝에 프롬프트에 있던 청크의 유효한 인용을 달게 합니다. 3단계에서 생성 실패 6건의 원인이 제각각이어서, 판정 모델 없이 자동으로 측정되는 형식 과제로 좁혔습니다.

**학습 데이터** (`data/sft`, 학습 125개 + 검증 13개)
- 출처 청크 235개에서 기반 모델(Qwen3-4B-Instruct-2507)이 질문을 만들고, 평가와 같은 RRF+리랭커 검색으로 컨텍스트 5개를 붙입니다. 출처 청크가 5개 안에 있는 182개 중, 프롬프트마다 4개 답을 샘플링해(온도 0.7) 모든 문장에 유효한 인용이 있고 출처 청크를 인용한 답이 하나라도 있는 138개를 남겼습니다(기반 모델 자기 증류 + 필터). 샘플 전체의 문장 단위 인용률 평균은 0.881이었습니다.
- 질문 언어는 ko/en/de를 순환하고, 학습 예시 125개 중 48.8%가 질문과 출처 문서의 언어가 다릅니다.
- 평가셋과의 분리: 평가 정답 청크는 출처로 쓰지 않았고, 평가 질문과 임베딩 유사도 0.80 이상인 질문은 버렸으며 같은 질문은 0개입니다. 다만 학습 프롬프트 138개 중 68개에는 평가 정답 청크가 검색된 컨텍스트로 들어 있습니다(손실이 걸린 답변이 아니라 컨텍스트입니다).

**학습** (`experiments/train_lora.py`, 트레이너 없이 직접 작성한 루프)
- 어댑터: rank 16, alpha 32, dropout 0.05, 모든 어텐션·MLP 선형층. 학습 파라미터 33.0M.
- 최적화: AdamW, lr 2e-4, 5% 워밍업 후 코사인 감쇠, 유효 배치 8(배치 1, 누적 8), 3 epoch, 그레이디언트 체크포인팅. 일반적인 기본값이고 튜닝하지 않았습니다.
- 손실은 답변 토큰에만 걸고 답변 구간의 로짓만 계산합니다. 전체 2300개 위치의 어휘 로짓을 계산하면 12GB GPU에서 메모리가 부족했습니다.
- QLoRA는 기반 가중치를 4비트 NF4(이중 양자화, bf16 계산)로 두고, LoRA는 기반을 bf16으로 둡니다. 나머지는 같습니다.

| 학습 비용 | QLoRA | LoRA |
|---|---|---|
| 기반 가중치 | 2.5 GiB | 7.5 GiB |
| 학습 중 최대 GPU 메모리 | 4.3 GiB | 9.4 GiB |
| 학습 시간 | 9.9분 | 9.7분 |
| 어댑터 크기 | 126MB | 126MB |
| 검증 손실 (학습 전 -> 최종) | 0.220 -> 0.216 | 0.109 -> 0.121 |

**평가**: 같은 프롬프트(cite_v1), 같은 상위 5개 컨텍스트, greedy 디코딩으로 평가 질문 45개를 생성했습니다. 양자화 효과와 학습 효과를 분리하려고 4비트 기반 모델(어댑터 없음)도 평가했습니다.

| 조건 | 문장 단위 인용률 | 인용 ID 유효 | 충실도 | 답변 관련성 | 정확성 |
|---|---|---|---|---|---|
| 기반 bf16 | 0.857 | 0.978 | 0.925 | 0.975 | 0.850 |
| 기반 4비트 | 0.636 | 0.978 | 0.976 | 0.976 | 0.780 |
| QLoRA 학습 (4비트 기반) | 0.946 | 0.956 | 0.976 | 0.927 | 0.780 |
| LoRA 학습 (bf16 기반) | 0.886 | 0.978 | 0.902 | 0.976 | 0.829 |

| 문장 단위 인용률의 차이 (쌍체 부트스트랩) | 평균 차이 | 95% 구간 | 좋아진 / 나빠진 질문 |
|---|---|---|---|
| 4비트 기반 - bf16 기반 (양자화 효과) | -0.221 | -0.308 ~ -0.133 | 2 / 24 |
| QLoRA - 4비트 기반 | +0.310 | +0.220 ~ +0.396 | 32 / 1 |
| QLoRA - bf16 기반 | +0.089 | +0.037 ~ +0.148 | 10 / 1 |
| LoRA - bf16 기반 | +0.028 | -0.014 ~ +0.076 | 6 / 3 |
| QLoRA - LoRA | +0.061 | +0.022 ~ +0.106 | 8 / 0 |

- QLoRA 학습은 인용 완결성을 유의하게 올렸습니다. 큰 개선폭의 대부분은 양자화로 떨어진 인용률을 회복한 것입니다. "QLoRA가 LoRA보다 낫다"가 아니라 "4비트 기반에서 학습이 열화를 메우고 bf16 기반 수준을 약간 넘었다"가 정확한 해석입니다.
- LoRA는 출발점(0.857)이 이미 높고 목표 답변이 그 모델 자신의 샘플이라 올릴 여지가 작았고, 개선은 확정되지 않았습니다.
- 답변 품질 판정은 조건 사이에서 최대 0.07 차이이고 질문 40~41개에서 답 하나가 약 0.025입니다. 형식 개선이 품질 악화로 얻어졌다는 증거는 없지만, 이 표본으로 차이가 없다고 확정할 수도 없습니다. 결과 유형 개수도 네 조건이 비슷합니다(ok 29~30).
- 학습 전 검증 손실이 QLoRA 0.220, LoRA 0.109로 두 배 다른 것은, 목표 답변이 bf16 모델 자신의 샘플이라 4비트 모델이 더 낮은 확률을 주기 때문으로 해석합니다(검증하지 않은 해석입니다).
- 학습 손실은 0.03까지 내려갔지만 검증 손실(13개)은 거의 변하지 않았습니다. 125개를 3번 돌리면서 과적합이 시작된 신호이고, 에폭 수는 튜닝하지 않았습니다.
- 어댑터를 병합하지 않아서 생성이 기반 모델보다 느립니다(질문당 중앙값: 기반 bf16 3.5초, QLoRA 10.0초, LoRA 6.9초).

## 실패 사례와 원인 분석

**1. BM25는 교차 언어에서 작동하지 않습니다.**
교차 언어 24문항에서 nDCG가 0.09~0.10입니다. 질문과 문서가 다른 언어면 공유하는 어휘가 거의 없기 때문입니다. de→en의 0.48은 예외인데, 해당 질문에 Brinelling, DIN 3761, needle 같은 공통 고유명사가 들어 있어 어휘가 겹친 결과입니다. 즉 이 0.48은 교차 언어 능력이 아니라 평가셋 구성의 결과입니다.

**2. RRF는 교차 언어에서 dense보다 나빴습니다.**
- 사실: 정답이 dense 상위 5에 있었는데 RRF 상위 5에서 빠진 질문이 11개이고, 11개 모두 교차 언어입니다. 반대로 RRF가 나은 질문은 4개입니다. 교차 언어 nDCG는 dense 0.345, RRF 0.092입니다.
- 원인(순위 단위로 확인): 정답 청크는 dense 목록에만 있고, 질문과 같은 언어의 청크는 BM25와 dense 양쪽에 올라 점수가 합쳐집니다. k=60에서는 1등(1/61)과 5등(1/65)의 점수 차이가 작아, 두 목록에 중간 순위로 같이 오른 청크가 한 목록의 1등을 이깁니다.
- 임시 확인: k를 60, 10, 1로 바꿔 보면 교차 언어 nDCG가 0.092, 0.174, 0.250으로 올랐고 단일 언어는 0.808, 0.820, 0.835로 소폭 올랐습니다. 이 계산은 결과 파일로 남기지 않은 임시 실행이고 질문 45개로 k를 고르면 평가셋에 맞춘 값이 되므로, 정식 실험으로 넣지 않았습니다.

**3. 리랭커가 가장 좋지만 같은 언어 쪽으로 기웁니다.**
RRF+리랭커가 상위 5에 정답을 하나도 넣지 못한 질문이 9개입니다. 9개 모두 1위 청크가 질문과 같은 언어입니다. 정답이 독일어에 있는 질문(ko→de 3개, en→de 3개)이 6개로 가장 많습니다.
- 확인된 것: 이 9개 질문에서 1위가 질문 언어의 문서였습니다.
- 가설(미검증): 영어·한국어 질문에는 같은 주제를 다루는 같은 언어 문서가 따로 있어, 독일어 문서에만 있는 세부 사실이 밀립니다. en→ko와 de→ko는 한국어 문서가 적고 짧아 dense 점수가 높게 나왔습니다(0.94, 0.74).
- 단, en→de의 dense 0.00은 질문 4개의 결과라 일반화하지 않습니다.

**4. 정제 실패가 일부 청크를 오염시킵니다.**
수식이 한 글자씩 쪼개져 들어온 청크가 대략 35개입니다(1~2자짜리 줄이 30줄을 넘는 청크로 센 근사치이며 정확한 오염 비율이 아닙니다). 예: `ko_bearing#5`는 Weibull 분포 수식의 조각으로 채워져 있습니다. 위키 TextExtracts가 수식과 표를 평문으로 바꾸는 과정에서 생겼고, 해당 청크는 임베딩과 BM25 품질을 떨어뜨립니다. 정제 개선 전후 비교는 하지 않았습니다.

**5. 평가셋 검수에서 나온 문제.**
표본 12개 중 2개가 부적합했습니다. 하나는 "이와 같은" 같은 지시어 때문에 앞 문맥 없이는 의미가 불완전한 문장을 핵심 근거로 쓴 것, 다른 하나는 '왜'를 묻는데 원인이 아닌 발생 조건 문장을 핵심 근거로 쓴 것입니다. 같은 유형이 나머지 33개에도 남아 있을 수 있습니다.

## 한계

- **표본 크기**: 질문 45개, 언어쌍별로는 2~9개입니다.
- **정답 누락**: 같은 사실이 다른 언어 문서에 더 있는데 정답으로 적지 못한 경우는 부당하게 오답 처리됩니다.
- **규모**: 346벡터에서 HNSW 효과를 볼 수 없었습니다.
- **측정 범위**: 검색은 사람이 붙인 정답으로 평가했고, 생성은 자동 형식 지표와 LLM 판정으로 평가했습니다. 사람 채점은 답변 8개뿐입니다.
- **판정 모델**: 충실도를 후하게 판정하는 경향이 사람 채점과의 불일치 2건에서 확인됐고, 표본 밖에서 판정 오류도 보였습니다. 판정 비율은 근사치입니다.
- **모델 비교**: 생성 모델은 하나이고 상업 API와 비교하지 않았습니다.
- **파인튜닝**: 학습 예시 125개, 시드 하나, rank 16 하나이고 하이퍼파라미터를 튜닝하지 않았습니다. 과적합 신호가 있고, 학습 프롬프트 일부에 평가 정답 청크가 컨텍스트로 들어 있습니다. 어댑터를 병합하지 않아 지연을 비교하기 어렵습니다.
- **형식 과제**: 인용 완결성은 답이 맞는지가 아니라 형식을 보는 지표입니다. 위 4개 조건의 답변 품질 차이는 이 표본으로 가려낼 수 없었습니다.
